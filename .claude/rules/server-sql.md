# Instance-aware queries

The query builders run their list and count queries as raw SQL through `prisma.$queryRawUnsafe` with `?` parameters, then load related entities in one batch per relation.

## Filter values

- Filter values reach the builders through the request parser (`utils/listRequest.ts`) as `FilterRef` pairs (`instanceId` undefined for a bare legacy id). Every builder is on the base (`services/query/EntityQueryBuilder.ts`) and takes the parsed request (`ParsedListRequest`, or `ClipListRequest` for clips) and matches every ref as an (id, instance) pair through `refClause`, `idClause` and `viaSceneClause` in `utils/sqlClauses.ts`: a ref with an instance matches that instance only, a bare ref its id on every instance (two Stash servers reuse small ids), and in the large shape a bare ref becomes one pair per allowed instance.
- A list request's `where` (`utils/whereTree.ts`, `parseWhere`) holds the user's rows: each leaf names its field's contract table key (tag `scenes` and `groups` too, which `<entity>_filter` nests under `scenes_filter`) and its criterion parses with the same schema as in `<entity>_filter`, refs kept as pairs. `ids` and `instance_id` are never rows. The limits (rows, groups, values, one level of groups) live in `WHERE_LIMITS` in `shared/types/filters/tree.ts`, counted after empty rows drop. Sorts that read a criterion take `topLevelCriteria`: the filter's, then a field's first root row of an "all" root that names something.
- Every ref keeps its instance through the depth expansion (`expandRefs` and `expandRefsEach` in `utils/hierarchyUtils.ts`, reached through `hierarchicalRefClause` in `services/query/EntityQueryBuilder.ts`): a ref with an instance expands within that instance's tree, a bare ref means every allowed instance (one root per allowed instance, each with that instance's descendants), and each descendant carries the instance it was found on. The hierarchy is one slim load per request over the involved allowed instances (`id`, `stashInstanceId` and `parentIds`, or `parentId` for studios, of the live rows), never one per ref, expanded in memory (23 to 33 ms at 10k tags). INCLUDES_ALL with a depth is one clause per selected ref, each with its own descendants, AND-ed: an entity holding any descendant of each chosen ref matches.
- A scene tag filter checks both the `SceneTag` junction and the `SceneInheritedTag` junction (an indexed copy of `inheritedTagIds`, keyed `(sceneId, sceneInstanceId, tagId, tagInstanceId)` with an index on the tag). Never read `inheritedTagIds` through `json_each` in a filter, count or exclusion statement; the JSON column is only for the API row transform.

## Every list query

- Exclusions: `LEFT JOIN UserExcludedEntity e ON ... AND (e.instanceId = '' OR e.instanceId = x.stashInstanceId)`, with `e.id IS NULL` in the WHERE. Never `NOT IN (...)` with one parameter per excluded entity: users with many exclusions exceed SQLite's bound-parameter limit (Prisma P2029).
- `x.deletedAt IS NULL`, because sync soft-deletes.
- The allowed-instances filter (`instanceClause(alias, ids)` or `instanceColumnClause(column, ids)` from `utils/sqlClauses.ts`, fed by `UserInstanceService.getUserAllowedInstanceIds`: enabled, selected (a selection naming no enabled instance means every enabled one) and past their first sync). The lookup throws on a database error; it never returns `[]` to mean "unknown". A request resolves the list once, in `requireCacheReady` (503 when empty), `requirePickerReady` (the six `/minimal` pickers only: an admin's `scope: "allEnabled"` reads `getEnabledSyncedInstanceIds()`; the scene picker refuses the scope) or `withAllowedInstances` (no 503: playlists, user stats, the timeline). Each puts it on `req.allowedInstanceIds`, which handlers wrapped in `libraryHandler` read. Controllers never call `getUserAllowedInstanceIds` (lint); `routeGuards.test.ts` checks every `libraryHandler` route has one of the three. Its `OR stashInstanceId IS NULL` arm is dead, since the column is NOT NULL; don't copy it into new queries. The base builder's `instanceClause` (`utils/sqlClauses.ts`) takes a required list, and an empty list matches nothing (`1 = 0`); every list route also stands behind `requireCacheReady`, which answers 503 first. One exception: the `/minimal` pickers' `scope: "allEnabled"` (the admin's Content Restrictions editor) swaps it for `getEnabledSyncedInstanceIds()` and leaves out the exclusion join (owner, 2026-09-28: an admin may restrict what they hid), for an ADMIN only (403 otherwise, in `findMinimalEntities`); `deletedAt` stays.
- A ref set has two shapes (`PAIR_INLINE_LIMIT`, 64): up to it the refs are bound inline as OR-ed pairs in one correlated `EXISTS` (or on the row itself); above it they travel as one JSON parameter into a materialized CTE, the matched entities into a second, and the list matches them with a row-value `IN` on its primary key (INCLUDES: 4 ms for 1,000 ids at 200k scenes). An EXCLUDES (and a favourite filter's `false`) stays inline only up to `NEGATIVE_INLINE_LIMIT` (8) refs; above it each row probes the refs CTE with no matched set (`excludesRefsProbe`): a junction keeps a keyed `NOT EXISTS` per junction whose rows match `(+j.refId, j.refInstance) IN (SELECT id, inst FROM <name>_refs)`, a column matches its key as one text key `NOT IN` the refs' keys and keeps a row with no value. Inline pairs cost each row a comparison per ref (49 favourite tags no image holds: 181 ms against 125 at 142k images), and a matched set costs every junction row of the refs (40 common tags at 207k scenes: 584 ms against 37) (F11b). A matched set used with `NOT IN` must hold no NULL (one NULL makes `NOT IN` match nothing), so it is built only from NOT NULL key columns. Never place a ref list inside a correlated subquery (re-evaluated per row, 12 s at 200k) and never a row-value `NOT IN (subquery)` (the set is scanned per row: 78 s for 179k rows); a `LEFT JOIN ... IS NULL` anti-join or `NOT EXISTS` on a `json_each`-fed CTE gets no automatic index (5 s at 1,000 ids).
- The scene tag filter's INCLUDES takes its shape from how each statement reads its rows (`sortedByIndex` in `refClause`, set by `SceneQueryBuilder.tagClause` from `QueryContext.sortField`; `hierarchicalRefClause` attaches the no-order shape as the clause's count form, `FilterClause.count`, which the base's count statement uses). A page under a sort with a browse index (created_at, updated_at, date, title, duration, performer_count, tag_count) walks the index and stops at the page: up to 64 refs the correlated EXISTS (2 ms a page at 200k scenes, where building a list first costs 30); above 64 the junction rows of the refs CTE, read by `SceneTag`'s tag index as a row-value IN, with the inherited arm probing the refs and no matched set (72 refs: 407 ms against 842 for a common set, 9 against 145 for a rare one). The count, and a page under a sort without an index (the viewer's rating, plays, O count, last played, random, the file columns), read every match: up to 64 refs a row-value IN over `SceneTag`'s tag index (at 200k a page 6 to 61 % faster than the EXISTS, a count 8 to 43 %: a tag of 634 scenes counts in 94 ms against 164); above 64 the matched set (the refs-CTE list made a rare set's count 6 % slower and its rating page 38 % slower). EXCLUDES keeps its shapes. A materialized CTE probed with `IN` from inside a correlated subquery is built once (plan `LIST SUBQUERY`, not `CORRELATED LIST SUBQUERY`). The inherited arm mirrors the direct one on `SceneInheritedTag` (`inheritedJunction` in `refClause`): a second EXISTS OR-ed in the per-row shape, a `UNION ALL` of both junctions in the list and count shapes, and a UNION of both in the matched set (a rare tag's count at 200k: 96 to 33 ms).
- The base builder owns these clauses, the exclusion join, `deletedAt`, the allowed instances, the `ids` filter, the random sort's bound seed and the joined `COUNT(*)`; a builder declares its spec, its filter clauses as a `fieldClauses` table (one function per field of its filter, `ids` aside) and a `searchClause`, its sort map, row transform and relations. The base reads the filter as leaves (one criterion of one field) and builds each leaf's clause through `clauseFor` in the table's order, the search last. Every CTE name derives from the leaf's name (`LeafContext.name`, unique in the statement: the `tags` leaf adds `tags_refs` and `tags_matched`), and `combine` throws on two CTEs of one name.
- A list statement is `<base> AND <filter> AND <where> AND <search>`: the request's `where` tree (`whereClauses` in `EntityQueryBuilder.ts`) compiles after the filter's leaves and before the search, so no "any" group ever ORs with a base clause. Tree leaves are numbered depth-first and named `w<n>_<field>` (their CTEs `w0_tags_refs`, ...). In an "any" container (the root included) same-field rows merge first (`mergeAnyLeaves` in `utils/whereTree.ts`, through shared `anyMergeKey` and `anyMergeCap`): twenty one-tag rows read the junction once. Under an any group the scene, image and clip junction refs take the read-once shape (`refOptionsOf`, and `hierarchicalRefClause` defaults `sortedByIndex` to false), since an OR cannot walk one arm in a sort index's order; `viaSceneClause` (performer, studio and tag lists filtered by scene refs) has no `sortedByIndex` and keeps its shape. A leaf's excludes (`<name>_not`) stay AND-ed with it, one disjunct of the group. An "all" root's leaves are separate clauses, so a flat tree's statement is the filter object's but for the CTE names; a group keeps its children's count forms. No field clause may join (`anyOf` throws on one; a table-driven test over every builder holds it). Sorts that read a criterion (Scene Number, Playlist order, Collection order) and the clip list's `lists` flag read the top level only: `topLevelCriteria` and `topLevelLeaves`, the filter plus the root rows of an "all" where, never a row inside a group or under an "any" root.
- Every order ends with the primary key, `x.id <dir>, x.stashInstanceId <dir>`, which the base appends; a spec's `tiebreak(field)` holds only the terms before it (the name after a count), so rows equal on everything else (one name twice, one id on two servers, one random value, NULLs) keep one order on every page.
- Per-user fields are the viewer's rows only, in the filter, the sort and the row alike, never a fallback to the Stash column (`x.rating100`, `x.oCounter`), which belongs to the Stash user. A sort reads an unrated row as 0 (`COALESCE(r.rating, 0)`); a filter on a number a row may lack (the rating, a height, a weight, a duration) reads the bare column (`r.rating`), so an unknown value matches no comparison, NOT_EQUALS and NOT_BETWEEN included, and only IS_NULL finds it (`buildNumericFilter`; the fields that offer IS_NULL and NOT_NULL are declared `nullableNum()` in `shared/types/filters/fields.ts`). Counts, plays and O counts are never missing (none is 0) and keep their `COALESCE`.
- A list's per-row relations load by the row's (id, instance): one statement per relation for the page, driven from the page's pairs (`WITH page(pid, pinst) AS (SELECT json_extract(value, '$[0]'), json_extract(value, '$[1]') FROM json_each(?)) ... FROM page pg CROSS JOIN <Junction> j ON j.<parent>Id = pg.pid AND j.<parent>InstanceId = pg.pinst`), never `j.<parent>Id IN (?)` on bare ids, which merges two servers' same-id rows.
- A list row's nested refs (a scene's performers, tags, collections, galleries, studio and inherited tags; a gallery's, an image's or a collection's studio; a clip's tags) load through `services/query/nestedRefs.ts`: `loadNestedRefs` over a junction or the row's own table, `loadRefsByKey` for a column of the row. Each keeps only live entities with no exclusion row for the viewer on the entity's instance, one statement per relation for the page: a parent's visibility never settles its refs', since cascades are first order. A ref carries names, images and links; never select `x.favorite` or `x.rating100` for one (they are the Stash user's). A tag's and a studio's own hierarchy load the same way: the parents through `loadRefsByKey` (a tag's `parentIds`, a studio's `parentId`, on the row's own instance), a studio's children through `loadNestedRefs` with `StashStudio` as its own link (`StashStudio_parentId_idx`), a tag's through `loadTagChildren` (`parentIds` is JSON with no index, so one statement reads the live tags once through `json_each(x.parentIds)` and keeps the page's (id, instance) pairs: 1.6 ms at 10k tags). A parent the viewer cannot see is left out (a studio's is null), as a child is.
- A spec's `joins` holds static LEFT JOINs the select list reads (the gallery's cover image), each on a unique key so `COUNT(*)` stays exact. A per-row count the page shows (a gallery's visible scenes) is one statement for the page driven from its pairs (`json_each(?)` with `CROSS JOIN`), not a correlated column: a column is evaluated for every row fed to a temp B-tree sort.
- A nested entity (a clip, shown only while its scene is) declares its parent in the spec: the parent as a static INNER JOIN on its key (`joins`), the parent's exclusion join through `exclusionJoin` (`utils/sqlClauses.ts`) in `extraJoins(ctx)`, only when `ctx.applyExclusions`, and the parent's `deletedAt IS NULL` and exclusion check in `extraBaseWhere(ctx)`; the list, the count, `getByRefs` and `readAll` all get them.
- The count is `COUNT(*)`, exact because every other LEFT JOIN is on a unique key (the per-user rows by user, instance and entity) and the exclusion join is an anti-join (`e.id IS NULL`). A new LEFT JOIN that can match several rows overcounts silently: filter with `EXISTS` instead.
- BigInt columns such as `fileSize` go through `Number()` in `transformRow`. Row types live in `server/types/internal/queryRows.ts`.
- Scene sorts on an index: `created_at`, `updated_at`, `date` and `duration` through `(deletedAt, X DESC, id DESC, stashInstanceId DESC)`, and `title`, `performer_count` and `tag_count` through the stored `titleSort`, `performerCount` and `tagCount` with `(deletedAt, X, id, stashInstanceId)`; images by created_at through `StashImage_browse_idx` of the same shape. A browse index covers the whole ORDER BY, the list's key included: Prisma's SQLite is built with STAT4 and ignored the two- and three-column browse indexes (it scanned the table and sorted every row, 255 to 385 ms a page at 200k), while the host sqlite3, without STAT4, used them, so a CLI-only plan hid it. `titleSort` is the displayed title (the title, else the file name without its extension), lower-cased by SQLite's `lower()`, which folds ASCII only; `performerCount` and `tagCount` count the scene's `ScenePerformer` and `SceneTag` rows. `refreshSceneDerivedColumns` (`SCENE_DERIVED_COLUMNS_SQL` in `StashSyncService.ts`) writes all three after the junction inserts of every scene batch; anything else that writes a scene or its junction rows calls it too. The per-user sorts (rating, plays, O count) and random sort in a temp B-tree.
- The random sort reduces `% 2147483647` at each step to keep large seeds in integer range.
- A sort that needs a request-dependent join (the collection page's `scene_index` through `SceneGroup`) is a sort-map key only when the filter supplies what it joins on, and the parser marks the sort invalid without it (a 400 in reject mode, the default sort in drop mode).
- A per-row expression that parses text (Career Length's `careerYearsSql` in `utils/sqlClauses.ts`) is a scalar subquery whose nested FROM computes the normalised text and its parts once: an inline expression repeats every function at each reference, three times as slow (64 ms against 202 over 55k performers). Nothing indexes it, so a page sorted by it reads and sorts every live row (110 ms at 55k performers, 21 ms on prod); its sort puts unknowns last with `NULLS LAST`.
- A handler that sends several heavy raw statements runs them in turn, not through `Promise.all`: sent together through Prisma's pool they contend (the stats page at 200k scenes: 0.12 s in turn against 0.28 s together; A6's ranking reads 0.05 to 0.16 s each in turn against 0.6 to 1.6 s). Light statements (a page's relation loads, 1 to 2 ms each) show no difference either way.
- A change stamp (a cache kept while its inputs are unchanged, as `RecommendationService` does) reads `COUNT(*)` with `MAX(id)` over a table with `AUTOINCREMENT` ids (inserts are monotonic, deletes change the count), and a timestamp only where rows change in place (`updatedAt`, `lastPlayedAt`). `UserExcludedEntity.computedAt` holds epoch milliseconds from Prisma and text from `CURRENT_TIMESTAMP` in tests and scripts, and `MAX()` over mixed storage classes returns the text.
- Text search binds `likeContains(q)` (`utils/sqlHelpers.ts`) with `LIKE ? ESCAPE '\'`, so `%`, `_` and `\` in the text match themselves. SQLite's LIKE folds ASCII case only, and a JSON list column (`aliasList`, `aliases`, a URL list) is matched one element at a time through `jsonListArm(column, param)` (`utils/sqlHelpers.ts`), never as its JSON text (a `[` or `"` would match every row with a list). Every list search (`q`) and the pickers' goes through one helper: `searchTerms(q)` (`utils/sqlHelpers.ts`: words split on whitespace, "quotes" for a phrase, duplicates collapsed, at most 10) and `searchAll(terms, termClause)` (`utils/sqlClauses.ts`: every term must match, each term's arms bound to its `likeContains` pattern). There is no `LOWER()` and no JavaScript lower-casing: SQLite's LIKE folds ASCII case, and a non-ASCII letter matches as typed. A gallery's searched name is `galleryNameSql(alias)` (title, else the file's name without its extension, else the folder's name), also read by the Title filter and the picker. The per-field text filters (`buildTextFilter(criterion, column | null, { also?, lists? })` in `utils/sqlClauses.ts`) escape the same way, without `LOWER()`, as one phrase (no word split); a null column filters the lists alone (IS_NULL matches NULL, `''` and `'[]'`), and the performer name filter and the pickers match each alias on its own.
- The database has planner statistics (migration `20260925001100` runs `ANALYZE`, and each sync that wrote runs `PRAGMA optimize`), so a plan on the replay's small tables says little. Run a bench copy's `ANALYZE` through Prisma or the migrations, never the sqlite3 shell's `ANALYZE`, which drops the STAT4 samples every migrated database has and changes plans (it misled PR 4's clip-list finding). Time a new list query on a 200k-scene copy with `server/scripts/db-bench/` (its README), before and after, and time the builder call through Prisma too: Prisma's bundled SQLite can plan a statement differently from the sqlite3 CLI (the old image page: 220 ms through Prisma, 1 ms in the CLI).
- To count an entity's live scenes across a whole junction, count all its junction rows (a covering-index scan) minus the rows of soft-deleted scenes (`StashScene s CROSS JOIN <Junction> j ... WHERE s.deletedAt IS NOT NULL`). Joining every junction row to `StashScene` for `deletedAt` reads a table row per junction row: 0.4 s for `ScenePerformer` and 0.6 s for `SceneTag` at 200k scenes, against 0.1 s and 0.15 s.
- A scoped count of the same kind subtracts the soft-deleted side's rows found from the entity table's `deletedAt` index, with the scope's pairs a `+`-column filter (`(+j.a, +j.b) IN (SELECT ... FROM pairs)`): as an index constraint SQLite probes every pair for every deleted row (118k deleted images on the prod snapshot).
- A card's count column is the tab's live total before the viewer's exclusions, kept by `LinkCountService` (sync.md). The builders subtract `UserExcludedContentCount` (`services/query/excludedCounts.ts`: joined once by its primary key when the viewer's exclusions apply; every count column, count sort and count filter reads `MAX(column - COALESCE(d.<relation>, 0), 0)`). A count expression (a `MAX`, a subtraction) comes back from Prisma as bigint where the plain column comes back as number, so a row type reads `number | bigint`.

## Lookups

- The per-entity getters `get<Entity>(id, instanceId)` and most `get<Entity>sByIds` require an instanceId. Many other `StashEntityService` methods (name maps, counts, cross-entity lookups) ignore instances; check before relying on one.
- `getByRefs` (the base builder's) matches its refs through `idClause`: inline pairs up to 64, the materialized set above (1,000 refs: 4 ms at 200k scenes). It runs no count and takes `FilterRef`s: a bare ref matches its id on every allowed instance (the clip by id). Read a list page (`PER_PAGE_MAX`) of refs per call, as `PlaylistQueryService` does, so a page's relations stay one batch. `readAll` (protected) reads every row of a request with no page and no count, for a set its filter bounds (a scene's clips).
- A per-user page (the stats page) keeps a per-user row only while its entity shows: `CROSS JOIN <Entity> x ON x.id = h.<id> AND x.stashInstanceId = h.instanceId AND x.deletedAt IS NULL`, the exclusion join on `h.instanceId`, the allowed instances on `x`, driven from the user's rows (`visibleEntity` in `UserStatsAggregationService`).
- A name a row needs from another table (a scene's studio and inherited tag names) is read for the request from the ids at hand, by (id, instance) (`hydrateNames` in `StashEntityService.ts`). A name cache over a synced table needs a caller that clears it after every sync, or is dropped: the whole-table name maps `StashEntityService` once kept had none and went stale.
- In-memory maps key on `entityKey(id, instanceId)` from `utils/entityRef.ts` (`` `${id}\0${instanceId}` ``), and a key of other parts (type, id and instance; a relation's two ids) on `compositeKey(...)`. The module also holds `EntityRef`, `distinctRefs` and `pairsJson`. Lint rejects a template or string holding `\0` anywhere else in the server source.
- A query that drives from a bound JSON list (`json_each(?)`) into an entity table joins it with `CROSS JOIN`, so SQLite keeps `json_each` as the outer loop and looks each ref up by primary key. A plain `JOIN` can make it scan the table and re-read the JSON for every row (27.7 s for 5,000 refs against 26k scenes; 10 ms with `CROSS JOIN`). Check with `EXPLAIN QUERY PLAN`: `SCAN j`, then `SEARCH x USING ... PRIMARY KEY`.
- A JSON list column read with `json_each` goes through `jsonListOrEmpty` (`utils/sqlJson.ts`): text that is not JSON, or NULL, reads as an empty list, where a bare `json_each` fails the whole statement with "malformed JSON" (a tag's `parentIds` in the tag lists, the tag tree and the exclusion recompute).
- The same holds for a user's own rows driving lookups into a big table: `WatchHistory w CROSS JOIN StashScene s ON s.id = w.sceneId AND s.stashInstanceId = w.instanceId`. Without it SQLite may walk every live scene through a `(deletedAt, ...)` index and probe the history (`RankingComputeService`: 124 ms against 26 ms at 200k scenes).
- A detail page's tab counts are `countRelations` (`services/RelationCounts.ts`): each tab's list builder's `count` over the request its grid sends, parsed by `parseListRequest`, with a depth only on contract-hierarchical fields; behind `GET /api/library/<type>s/:id/counts` (`requireCacheReady`, `canUserAccessEntity` 404). A detail lookup answers the builder's row unchanged, so its counts are the card's.
- A per-user write (rating, play, O press, image view, hide, playlist item) names its entity's instance in the request. The handler calls `requireInstanceId` (`utils/routeHelpers.ts`), then `resolveAccessibleInstanceId` (`canUserAccessEntity`); a missing or empty instance answers 400, a copy the user cannot see 404. The server never picks an instance.

## Writes

- The writer rule: every transaction, every multi-row statement (`createMany`, `INSERT ... SELECT`, a whole-table `UPDATE`, a chunked delete) and every single-row write on a user path (ratings, favorites, O counts, plays, image views, hides, stats, playlists, restrictions) is a unit of the writer queue in `server/utils/dbWrite.ts`. Units run one at a time, in arrival order. `dbWrite(label, fn)` for statements, `dbWriteTransaction(label, fn)` for an interactive transaction, `dbWriteBatch(label, [...])` for a batch; the label ("rating.scene", "sync.scenes") names the unit in the logs. Other single-row writes (settings, setup, groups, themes, carousels, downloads, auth) stay autocommit and wait in SQLite's `busy_timeout` (5 s).
- Why a queue in Node: Prisma's SQLite driver waits for the write lock on the query engine's worker threads (one per CPU). A few waiting writers occupy them all, the lock holder cannot run its next statement, and they time out together (P1008: 32 of 40 simultaneous hides failed on a 16-CPU box). A unit waiting in the queue holds no connection and no engine thread.
- No unit holds the lock longer than 1 s on a 200k-scene library (`DB_WRITE_HOLD_WARN_MS`): longer work is chunked (one unit per sync page, per user's exclusion swap, per 500 to 5,000 rows), so user writes interleave with it. Build every statement before the unit starts, and make no Stash request inside one. A unit over the bound logs `Database write held the lock {label, ms}`; one that waited in the queue longer than 10 s logs `Database write waited for the queue {label, ms, behind}`, naming the unit ahead of it.
- A busy failure (the lock held from outside the queue: the sqlite3 CLI, another process) reruns the unit from the start for up to 30 s, logging `Database write waiting for the lock`, so `fn` keeps no state between attempts. Any other error, a transaction's own timeout (P2028) included, is thrown at once.
- Nesting: inside a `dbWriteTransaction` callback write through `tx`, never through `dbWrite`; a nested unit throws `dbWrite re-entered: <outer> -> <inner>` in tests and development and logs it and runs inline in production. Never take the compute connection (`withComputeConnection`) inside a unit: the order is the compute connection first, then the queue. The queue is a `createSerialQueue` (`utils/serialQueue.ts`), as are the compute connection and manual backups: one at a time in arrival order, a rejected unit releases the next, and a nested `withComputeConnection` fails the same way (`withComputeConnection re-entered: <outer> -> <inner>`).
- Reads never queue: under WAL a read waits only for a pool connection and an engine worker, never for the writer. The one write that waits on readers is `wal_checkpoint(TRUNCATE)` (`checkpointWal` in `utils/databaseMaintenance.ts`, after the post-sync steps and at shutdown): it holds the lock while readers of older pages finish, up to `busy_timeout`, and the queue waits behind it.
- A batch computed from reads that a later change can make obsolete while it waits its turn (a ranking recompute after `forget`) goes through `dbWriteBatchIf(label, wanted, ops)`: the statements are built first and `wanted` is asked from memory when the unit starts. State in memory that a change makes obsolete is forgotten in the change's own unit (`afterCommit` on `dbWriteBatch` and `dbWriteTransaction`), so no unit queued behind it passes its check. `afterCommit` runs under the write lock: keep it synchronous and cheap. `dbWriteBatchIf` takes `afterCommit` too; it runs only when the batch was written.
- A play and an O press write their performer, studio and tag stats inside their history transaction (`statsWritesForScene` reads the scene before the unit and returns the upserts to run on `tx`), so a play is stored with its stats or not at all. `rebuildAllStatsForUser` writes through `dbWriteBatchIf` against the user's write generation, which every history unit that changes plays or O presses bumps in its `afterCommit` (play, O, a history clear, an import page that wrote); a rebuild that finds it moved reads again, up to four reads, then keeps the stats. A written rebuild forgets the rankings in its own `afterCommit`. A Sync from Stash history page writes its stats in its own unit (`statsWritesForScenes`), so a rebuild that keeps the stats is sound.
- A data migration that rewrites a column users also save (presets, carousel rules) writes with the value it read in the WHERE (`UPDATE ... WHERE id = ? AND col = ?`, the text read through `CAST(col AS TEXT)`, as `cleanStoredFilters` does in `DataMigrationService.ts`). Data migrations run after the startup sync while the API already listens, so a save in between wins and the update counts 0. Prisma's Json `equals` on SQLite compares `JSON.stringify` text byte for byte and misses text written in another format, so compare the raw text. Data migration 010 rebuilds link counts compare-and-set (`rebuildLinkCounts("all", { onlyIfUnchanged: true })`).
- Settings stored as JSON on `User` (saved Views and their defaults, pinned filters: `filterPresets`, `defaultFilterPresets`, `filterPins`) write compare-and-set through `updateUserJson` (`utils/userJsonColumn.ts`), never `prisma.user.update`: it reads `CAST(col AS TEXT)` for the columns it changes, applies the change, and writes them all in one `UPDATE ... WHERE id = ? AND CAST(col AS TEXT) IS ?` (NULL-safe) that also sets `updatedAt` (raw SQL skips `@updatedAt`; Prisma stores epoch milliseconds as an integer). A lost race re-reads and retries up to 3 times, then answers 409. A settings write, so autocommit, not a `dbWrite` unit.
- A `PrismaPromise` runs when `.then` is first called. A timing wrapper that calls `.then` (or `Promise.resolve(p)`) on a statement bound for `dbWriteBatch` runs it at once outside the batch, and the batch runs it again; time the unit instead.
- Lint: `prisma.$transaction` outside `utils/dbWrite.ts` is an error (`no-restricted-syntax`; tests may mock it).
- `configureSQLite`'s performance PRAGMAs (`synchronous = NORMAL`, cache, mmap) reach only the pooled connection that ran them; the compute connection sets its own `cache_size` and `synchronous`. A timing taken through the pool may run on a connection with SQLite's defaults (2 MB cache, `synchronous = FULL`).

## `||` defaults

A `||` on an id, an instance id or a count needs a `??` review before it changes: `""` means every instance (in the exclusion and hidden-entity tables, say) and `0` is a real count, so `||` may be replacing a meaningful value. `prefer-nullish-coalescing` flags them; the unreviewed ones sit in `server/eslint-suppressions.json`.

## SQLite numbers

SQLite can return `5.0000000001` from an integer column, and BigInt from a large one. Wrap counts in `Math.round(Number(x))` before writing them to an `Int` field (#410), and convert BigInt with `Number()` before JSON.

Stash's timestamps (`stashCreatedAt`, `stashUpdatedAt` on every cached type) hold epoch milliseconds like Prisma's own DateTimes, since migration `20261002000600`; sync stored Stash's RFC 3339 text before it. Compare them as numbers.

Date filters go through two builders in `utils/sqlClauses.ts`, one rule for both: a `YYYY-MM-DD` value is a whole day (EQUALS in it, GREATER_THAN after it, LESS_THAN before it, BETWEEN both days included and one side alone open-ended), a row without a date matches only IS_NULL, and no negative has an `IS NULL` arm. `buildDayFilter(c, col)` takes Stash's text days (`date`, `birthdate`, `deathDate`) as `substr(fullDateSql(col), 1, 10)`, so a `YYYY` or `YYYY-MM` value is its first day. `buildInstantFilter(c, col, ctx.timeZone)` takes epoch columns (`stashCreatedAt`, `stashUpdatedAt`, `w.lastPlayedAt`): a day is `[its first instant, the next day's)` in the viewer's zone (`utils/zonedTime.ts`, DST and skipped midnights included), a date-time its millisecond. The zone is `QueryContext.timeZone`: `middleware/requestTimeZone.ts` reads `X-Peek-Time-Zone` (a valid IANA name, else "UTC") onto `req.timeZone`, and every caller of a builder's `execute` or `count` passes `timeZone: req.timeZone` beside `allowedInstanceIds`; an internal caller that passes none gets "UTC".

Prisma's raw queries return `COUNT`, `SUM` and `COALESCE` over integers as `bigint`, a `BIGINT` column such as `fileSize` as `bigint`, a `BOOLEAN` column as `boolean` (never 0 or 1), and a `DATETIME` column as a `Date`, whether it holds text or epoch milliseconds (text it cannot parse fails the query). A raw row type says so, and its `Number()` stays: `no-unnecessary-type-conversion` flags one only when the row type wrongly claims `number`. A transform writes a `Date` out with `toISOString()`, the string the JSON carried anyway.

- The clip list: `StashClip_browse_idx` (deletedAt, stashCreatedAt DESC, id, instance, title, isGenerated, scene key) drives the default list; the spec's `+s.deletedAt IS NULL` keeps the scene's `deletedAt` from driving the join. Clip tag, scene tag and performer INCLUDES read their junction as an IN list (`sortedByIndex: false`) except with a studio or scene filter at the top level (the filter, or a root row of an "all" where), which keeps the per-clip EXISTS (a leaf under an any group reads its list whatever drives); scene tags go through the clip's own scene key (`parentKey: ["c.sceneId", "c.sceneInstanceId"]`) and match inherited tags too.
