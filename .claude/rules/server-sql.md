# Instance-aware queries

The query builders run their list and count queries as raw SQL through `prisma.$queryRawUnsafe` with `?` parameters, then load related entities in one batch per relation.

## Filter values

- Filter values reach the builders through the request parser (`utils/listRequest.ts`) as `FilterRef` pairs (`instanceId` undefined for a bare legacy id). Every builder is on the base (`services/query/EntityQueryBuilder.ts`) and takes the parsed request (`ParsedListRequest`, or `ClipListRequest` for clips) and matches every ref as an (id, instance) pair through `refClause`, `idClause` and `viaSceneClause` in `utils/sqlClauses.ts`: a ref with an instance matches that instance only, a bare ref its id on every instance (two Stash servers reuse small ids), and in the large shape a bare ref becomes one pair per allowed instance.
- Every ref keeps its instance through the depth expansion (`expandRefs` and `expandRefsEach` in `utils/hierarchyUtils.ts`, reached through `hierarchicalRefClause` in `services/query/EntityQueryBuilder.ts`): a ref with an instance expands within that instance's tree, a bare ref means every allowed instance (one root per allowed instance, each with that instance's descendants), and each descendant carries the instance it was found on. The hierarchy is one slim load per request over the involved allowed instances (`id`, `stashInstanceId` and `parentIds`, or `parentId` for studios, of the live rows), never one per ref, expanded in memory (23 to 33 ms at 10k tags). INCLUDES_ALL with a depth is one clause per selected ref, each with its own descendants, AND-ed: an entity holding any descendant of each chosen ref matches.
- A scene tag filter checks both the `SceneTag` junction and the `inheritedTagIds` JSON column through `json_each`.

## Every list query

- Exclusions: `LEFT JOIN UserExcludedEntity e ON ... AND (e.instanceId = '' OR e.instanceId = x.stashInstanceId)`, with `e.id IS NULL` in the WHERE. Never `NOT IN (...)` with one parameter per excluded entity: users with many exclusions exceed SQLite's bound-parameter limit (Prisma P2029).
- `x.deletedAt IS NULL`, because sync soft-deletes.
- The allowed-instances filter (`buildInstanceFilter`, fed by `UserInstanceService.getUserAllowedInstanceIds`: enabled, selected (a selection naming no enabled instance means every enabled one) and past their first sync). Its `OR stashInstanceId IS NULL` arm is dead, since the column is NOT NULL; don't copy it into new queries. The base builder's `instanceClause` (`utils/sqlClauses.ts`) takes a required list, and an empty list matches nothing (`1 = 0`); every list route also stands behind `requireCacheReady`, which answers 503 first. One exception: the `/minimal` pickers' `scope: "allEnabled"` (the admin's Content Restrictions editor) swaps it for `getEnabledSyncedInstanceIds()` and leaves out the exclusion join (owner, 2026-09-28: an admin may restrict what they hid), for an ADMIN only (403 otherwise, in `findMinimalEntities`); `deletedAt` stays.
- A ref set has two shapes (`PAIR_INLINE_LIMIT`, 64): up to it the refs are bound inline as OR-ed pairs in one correlated `EXISTS` (or on the row itself); above it they travel as one JSON parameter into a materialized CTE, the matched entities into a second, and the list matches them with a row-value `IN` on its primary key (INCLUDES: 4 ms for 1,000 ids at 200k scenes) or a single-column key `NOT IN` (EXCLUDES: SQLite builds an ephemeral index, 321 ms). That set must hold no NULL (one NULL makes `NOT IN` match nothing), so it is built only from NOT NULL key columns. Never place a ref list inside a correlated subquery (re-evaluated per row, 12 s at 200k) and never a row-value `NOT IN (subquery)` (the set is scanned per row: 78 s for 179k rows); a `LEFT JOIN ... IS NULL` anti-join or `NOT EXISTS` on a `json_each`-fed CTE gets no automatic index (5 s at 1,000 ids).
- The scene tag filter's INCLUDES takes its shape from how each statement reads its rows (`sortedByIndex` in `refClause`, set by `SceneQueryBuilder.tagClause` from `QueryContext.sortField`; `hierarchicalRefClause` attaches the no-order shape as the clause's count form, `FilterClause.count`, which the base's count statement uses). A page under a sort with a browse index (created_at, updated_at, date, title, duration, performer_count, tag_count) walks the index and stops at the page: up to 64 refs the correlated EXISTS (2 ms a page at 200k scenes, where building a list first costs 30); above 64 the junction rows of the refs CTE, read by `SceneTag`'s tag index as a row-value IN, with the inherited arm probing the refs and no matched set (72 refs: 407 ms against 842 for a common set, 9 against 145 for a rare one). The count, and a page under a sort without an index (the viewer's rating, plays, O count, last played, random, the file columns), read every match: up to 64 refs a row-value IN over `SceneTag`'s tag index (at 200k a page 6 to 61 % faster than the EXISTS, a count 8 to 43 %: a tag of 634 scenes counts in 94 ms against 164); above 64 the matched set (the refs-CTE list made a rare set's count 6 % slower and its rating page 38 % slower). EXCLUDES keeps its shapes. A materialized CTE probed with `IN` from inside a correlated subquery is built once (plan `LIST SUBQUERY`, not `CORRELATED LIST SUBQUERY`). The inherited arm is a per-row EXISTS in every shape and bounds them all: `inheritedTagIds` has no index, so every live scene's list is read (about 100 ms at 200k).
- The base builder owns these clauses, the exclusion join, `deletedAt`, the allowed instances, the `ids` filter, the random sort's bound seed and the joined `COUNT(*)`; a builder declares its spec, filter clauses, sort map, row transform and relations.
- Every order ends with the primary key, `x.id <dir>, x.stashInstanceId <dir>`, which the base appends; a spec's `tiebreak(field)` holds only the terms before it (the name after a count), so rows equal on everything else (one name twice, one id on two servers, one random value, NULLs) keep one order on every page.
- Per-user fields are the viewer's rows only, in the filter, the sort and the row alike: `COALESCE(r.rating, 0)`, never a fallback to the Stash column (`x.rating100`, `x.oCounter`), which belongs to the Stash user.
- A list's per-row relations load by the row's (id, instance): one statement per relation for the page, driven from the page's pairs (`WITH page(pid, pinst) AS (SELECT json_extract(value, '$[0]'), json_extract(value, '$[1]') FROM json_each(?)) ... FROM page pg CROSS JOIN <Junction> j ON j.<parent>Id = pg.pid AND j.<parent>InstanceId = pg.pinst`), never `j.<parent>Id IN (?)` on bare ids, which merges two servers' same-id rows.
- A list row's nested refs (a scene's performers, tags, collections, galleries, studio and inherited tags; a gallery's, an image's or a collection's studio; a clip's tags) load through `services/query/nestedRefs.ts`: `loadNestedRefs` over a junction or the row's own table, `loadRefsByKey` for a column of the row. Each keeps only live entities with no exclusion row for the viewer on the entity's instance, one statement per relation for the page: a parent's visibility never settles its refs', since cascades are first order. A ref carries names, images and links; never select `x.favorite` or `x.rating100` for one (they are the Stash user's). A tag's and a studio's own hierarchy load the same way: the parents through `loadRefsByKey` (a tag's `parentIds`, a studio's `parentId`, on the row's own instance), a studio's children through `loadNestedRefs` with `StashStudio` as its own link (`StashStudio_parentId_idx`), a tag's through `loadTagChildren` (`parentIds` is JSON with no index, so one statement reads the live tags once through `json_each(x.parentIds)` and keeps the page's (id, instance) pairs: 1.6 ms at 10k tags). A parent the viewer cannot see is left out (a studio's is null), as a child is.
- A spec's `joins` holds static LEFT JOINs the select list reads (the gallery's cover image), each on a unique key so `COUNT(*)` stays exact. A per-row count the page shows (a gallery's visible scenes) is one statement for the page driven from its pairs (`json_each(?)` with `CROSS JOIN`), not a correlated column: a column is evaluated for every row fed to a temp B-tree sort.
- A nested entity (a clip, shown only while its scene is) declares its parent in the spec: the parent as a static INNER JOIN on its key (`joins`), the parent's exclusion join through `exclusionJoin` (`utils/sqlClauses.ts`) in `extraJoins(ctx)`, only when `ctx.applyExclusions`, and the parent's `deletedAt IS NULL` and exclusion check in `extraBaseWhere(ctx)`; the list, the count, `getByRefs` and `readAll` all get them.
- The count is `COUNT(*)`, exact because every other LEFT JOIN is on a unique key (the per-user rows by user, instance and entity) and the exclusion join is an anti-join (`e.id IS NULL`). A new LEFT JOIN that can match several rows overcounts silently: filter with `EXISTS` instead.
- BigInt columns such as `fileSize` go through `Number()` in `transformRow`. Row types live in `server/types/internal/queryRows.ts`.
- Scene sorts on an index: `created_at`, `updated_at`, `date` and `duration` through `(deletedAt, X DESC, id DESC, stashInstanceId DESC)`, and `title`, `performer_count` and `tag_count` through the stored `titleSort`, `performerCount` and `tagCount` with `(deletedAt, X, id, stashInstanceId)`; images by created_at through `StashImage_browse_idx` of the same shape. A browse index covers the whole ORDER BY, the list's key included: Prisma's SQLite is built with STAT4 and ignored the two- and three-column browse indexes (it scanned the table and sorted every row, 255 to 385 ms a page at 200k), while the host sqlite3, without STAT4, used them, so a CLI-only plan hid it. `titleSort` is the displayed title (the title, else the file name without its extension), lower-cased by SQLite's `lower()`, which folds ASCII only; `performerCount` and `tagCount` count the scene's `ScenePerformer` and `SceneTag` rows. `refreshSceneDerivedColumns` (`SCENE_DERIVED_COLUMNS_SQL` in `StashSyncService.ts`) writes all three after the junction inserts of every scene batch; anything else that writes a scene or its junction rows calls it too. The per-user sorts (rating, plays, O count) and random sort in a temp B-tree.
- The random sort reduces `% 2147483647` at each step to keep large seeds in integer range.
- A handler that sends several heavy raw statements runs them in turn, not through `Promise.all`: sent together through Prisma's pool they contend (the stats page at 200k scenes: 0.12 s in turn against 0.28 s together; A6's ranking reads 0.05 to 0.16 s each in turn against 0.6 to 1.6 s). Light statements (a page's relation loads, 1 to 2 ms each) show no difference either way.
- A change stamp (a cache kept while its inputs are unchanged, as `RecommendationService` does) reads `COUNT(*)` with `MAX(id)` over a table with `AUTOINCREMENT` ids (inserts are monotonic, deletes change the count), and a timestamp only where rows change in place (`updatedAt`, `lastPlayedAt`). `UserExcludedEntity.computedAt` holds epoch milliseconds from Prisma and text from `CURRENT_TIMESTAMP` in tests and scripts, and `MAX()` over mixed storage classes returns the text.
- Text search binds `likeContains(q)` (`utils/sqlHelpers.ts`) with `LIKE ? ESCAPE '\'`, so `%`, `_` and `\` in the text match themselves. SQLite's LIKE folds ASCII case only, and a JSON text column (`aliasList`, `aliases`) is matched as its text. The scene, performer, studio, tag, gallery and group list search (`q`) binds it with `LOWER()` on both sides, the image and clip searches with plain `LIKE`; the per-field text filters (`buildTextFilter` in `utils/sqlClauses.ts`) do not escape (PR 9 decides, against Stash's semantics).
- The database has planner statistics (migration `20260925001100` runs `ANALYZE`, and each sync that wrote runs `PRAGMA optimize`), so a plan on the replay's small tables says little. Time a new list query on a 200k-scene copy with `server/scripts/db-bench/` (its README), before and after, and time the builder call through Prisma too: Prisma's bundled SQLite can plan a statement differently from the sqlite3 CLI (the old image page: 220 ms through Prisma, 1 ms in the CLI).
- To count an entity's live scenes across a whole junction, count all its junction rows (a covering-index scan) minus the rows of soft-deleted scenes (`StashScene s CROSS JOIN <Junction> j ... WHERE s.deletedAt IS NOT NULL`). Joining every junction row to `StashScene` for `deletedAt` reads a table row per junction row: 0.4 s for `ScenePerformer` and 0.6 s for `SceneTag` at 200k scenes, against 0.1 s and 0.15 s.

## Lookups

- The per-entity getters `get<Entity>(id, instanceId)` and most `get<Entity>sByIds` require an instanceId. Many other `StashEntityService` methods (name maps, counts, cross-entity lookups) ignore instances; check before relying on one.
- `getByRefs` (the base builder's) matches its refs through `idClause`: inline pairs up to 64, the materialized set above (1,000 refs: 4 ms at 200k scenes). It runs no count and takes `FilterRef`s: a bare ref matches its id on every allowed instance (the clip by id). Read a list page (`PER_PAGE_MAX`) of refs per call, as `PlaylistQueryService` does, so a page's relations stay one batch. `readAll` (protected) reads every row of a request with no page and no count, for a set its filter bounds (a scene's clips).
- A per-user page (the stats page) keeps a per-user row only while its entity shows: `CROSS JOIN <Entity> x ON x.id = h.<id> AND x.stashInstanceId = h.instanceId AND x.deletedAt IS NULL`, the exclusion join on `h.instanceId`, the allowed instances on `x`, driven from the user's rows (`visibleEntity` in `UserStatsAggregationService`).
- `getEntityInstanceId()` takes a bare id. If the id exists on several instances it returns the alphabetically first `stashInstanceId` and only logs. If it finds nothing, or the lookup throws, it returns the first configured instance. Prefer an instanceId from the request.
- In-memory maps key on `entityKey(id, instanceId)` from `utils/entityRef.ts` (`` `${id}\0${instanceId}` ``), and a key of other parts (type, id and instance; a relation's two ids) on `compositeKey(...)`. The module also holds `EntityRef`, `distinctRefs` and `pairsJson`. Lint rejects a template or string holding `\0` anywhere else in the server source.
- A query that drives from a bound JSON list (`json_each(?)`) into an entity table joins it with `CROSS JOIN`, so SQLite keeps `json_each` as the outer loop and looks each ref up by primary key. A plain `JOIN` can make it scan the table and re-read the JSON for every row (27.7 s for 5,000 refs against 26k scenes; 10 ms with `CROSS JOIN`). Check with `EXPLAIN QUERY PLAN`: `SCAN j`, then `SEARCH x USING ... PRIMARY KEY`.
- The same holds for a user's own rows driving lookups into a big table: `WatchHistory w CROSS JOIN StashScene s ON s.id = w.sceneId AND s.stashInstanceId = w.instanceId`. Without it SQLite may walk every live scene through a `(deletedAt, ...)` index and probe the history (`RankingComputeService`: 124 ms against 26 ms at 200k scenes).

## Writes

- The writer rule: every transaction, every multi-row statement (`createMany`, `INSERT ... SELECT`, a whole-table `UPDATE`, a chunked delete) and every single-row write on a user path (ratings, favorites, O counts, plays, image views, hides, stats, playlists, restrictions) is a unit of the writer queue in `server/utils/dbWrite.ts`. Units run one at a time, in arrival order. `dbWrite(label, fn)` for statements, `dbWriteTransaction(label, fn)` for an interactive transaction, `dbWriteBatch(label, [...])` for a batch; the label ("rating.scene", "sync.scenes") names the unit in the logs. Other single-row writes (settings, setup, groups, themes, carousels, downloads, auth) stay autocommit and wait in SQLite's `busy_timeout` (5 s).
- Why a queue in Node: Prisma's SQLite driver waits for the write lock on the query engine's worker threads (one per CPU). A few waiting writers occupy them all, the lock holder cannot run its next statement, and they time out together (P1008: 32 of 40 simultaneous hides failed on a 16-CPU box). A unit waiting in the queue holds no connection and no engine thread.
- No unit holds the lock longer than 1 s on a 200k-scene library (`DB_WRITE_HOLD_WARN_MS`): longer work is chunked (one unit per sync page, per user's exclusion swap, per 500 to 5,000 rows), so user writes interleave with it. Build every statement before the unit starts, and make no Stash request inside one. A unit over the bound logs `Database write held the lock {label, ms}`; one that waited in the queue longer than 10 s logs `Database write waited for the queue {label, ms, behind}`, naming the unit ahead of it.
- A busy failure (the lock held from outside the queue: the sqlite3 CLI, another process) reruns the unit from the start for up to 30 s, logging `Database write waiting for the lock`, so `fn` keeps no state between attempts. Any other error, a transaction's own timeout (P2028) included, is thrown at once.
- Nesting: inside a `dbWriteTransaction` callback write through `tx`, never through `dbWrite`; a nested unit throws `dbWrite re-entered: <outer> -> <inner>` in tests and development and logs it and runs inline in production. Never take the compute connection (`withComputeConnection`) inside a unit: the order is the compute connection first, then the queue. The queue is a `createSerialQueue` (`utils/serialQueue.ts`), as are the compute connection and manual backups: one at a time in arrival order, a rejected unit releases the next, and a nested `withComputeConnection` fails the same way (`withComputeConnection re-entered: <outer> -> <inner>`).
- Reads never queue: under WAL a read waits only for a pool connection and an engine worker, never for the writer. The one write that waits on readers is `wal_checkpoint(TRUNCATE)` (`checkpointWal` in `utils/databaseMaintenance.ts`, after the post-sync steps and at shutdown): it holds the lock while readers of older pages finish, up to `busy_timeout`, and the queue waits behind it.
- Lint: `prisma.$transaction` outside `utils/dbWrite.ts` is an error (`no-restricted-syntax`; tests may mock it).
- `configureSQLite`'s performance PRAGMAs (`synchronous = NORMAL`, cache, mmap) reach only the pooled connection that ran them; the compute connection sets its own `cache_size` and `synchronous`. A timing taken through the pool may run on a connection with SQLite's defaults (2 MB cache, `synchronous = FULL`).

## `||` defaults

A `||` on an id, an instance id or a count needs a `??` review before it changes: `""` means every instance (in the exclusion and hidden-entity tables, say) and `0` is a real count, so `||` may be replacing a meaningful value. `prefer-nullish-coalescing` flags them; the unreviewed ones sit in `server/eslint-suppressions.json`.

## SQLite numbers

SQLite can return `5.0000000001` from an integer column, and BigInt from a large one. Wrap counts in `Math.round(Number(x))` before writing them to an `Int` field (#410), and convert BigInt with `Number()` before JSON.

Prisma's raw queries return `COUNT`, `SUM` and `COALESCE` over integers as `bigint`, a `BIGINT` column such as `fileSize` as `bigint`, a `BOOLEAN` column as `boolean` (never 0 or 1), and a `DATETIME` column as a `Date`, whether it holds text or epoch milliseconds (text it cannot parse fails the query). A raw row type says so, and its `Number()` stays: `no-unnecessary-type-conversion` flags one only when the row type wrongly claims `number`. A transform writes a `Date` out with `toISOString()`, the string the JSON carried anyway.
