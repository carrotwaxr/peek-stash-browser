# Video and media proxy

Peek never transcodes. It proxies Stash's own HLS streams and media files, and the browser never talks to Stash directly.

## Invariant

No Stash host and no API key reaches the browser. The client gets media only through `/api/proxy/...`, `/api/scene/:sceneId/proxy-stream/...` and `/api/scene/:sceneId/caption`. The key travels upstream only: in an `ApiKey` header from `video.ts`, or as `apikey` on the server-side URL in `proxy.ts`, redacted in logs. Log any URL that can carry `apikey` or `sig` through `redactUrl` (`utils/logRedaction.ts`).

The one exception is `stashUrl`, the View in Stash link on library entities, which holds Stash's UI address: `buildStashEntityUrl` takes the viewer and returns null unless it is an admin, so handlers pass `req.user` (through `addStashUrl` and `executeCarouselQuery` for scenes).

## Building proxy URLs

- Raw Stash paths from the database become proxy URLs before any response, through `toProxyUrl(urlOrPath, instanceId)` in `server/utils/proxyUrl.ts` and nowhere else: `/api/proxy/stash?path=<path and query>&instanceId=<the entity's instance>`. The instance is required, since a URL without one is served by the highest-priority instance. It drops any `apikey` query parameter (Stash's stored paths carry none) and returns an existing `/api/proxy/` path as is.
- The server builds player stream paths in `StashEntityService.generateSceneStreams` from Stash's recorded choices (`streamDirect`, `streamMkv`, `streamResolutions`), only for single-scene lookups; the client uses the paths unchanged (`playerSources.ts`), in Stash's order except that Direct and MKV go after the transcodes when `canDecode` (`utils/browserPlayback.ts`, `canPlayType` on the file's codecs) says this browser cannot play the file. The source selector plugin (`plugins/source-selector.ts`, `SourceFallback`) is the one fallback path: a codec error loads the next source, a network error retries the same source after 1 s and 3 s first, and the hook's session check (`beforeFallback`) runs before either. The client builds no stream URL itself, only caption URLs in `videoPlayerUtils.ts`; `ExternalPlayerButton.tsx` takes its signed direct link from `POST /api/scene/:id/external-player-link` (`useExternalPlayerLink`) and prefixes `window.location.origin`.
- Sync reads Stash's choices from its labels into those three columns and never stores its URLs, which carry the Stash API key. The old `streams` column that held them is gone (`20260925000200_drop_scene_streams_and_recovery_key`).
- Sprite and VTT use Stash's id-keyed routes, `/scene/:id/vtt/{sprite,thumbs}`, not the hash-keyed paths Stash reports.

## Two proxies

- `video.ts` serves HLS playlists, segments and captions, and reads the instance from `?instanceId=`. Stash 0.31 lists HLS segments as `/scene/:id/stream.m3u8/<n>.ts?resolution=...` (its segment route is `stream.m3u8/{n}.ts`). `rewriteHlsPlaylist` turns the four URL shapes Stash emits (absolute URL, absolute path, relative path, bare segment) into `proxy-stream` URLs that this same controller serves, so a rewrite bug breaks every segment request after it. URI attributes in tags (`#EXT-X-KEY`, `#EXT-X-MAP`, ...) go through the same rewrite (`rewriteStashUri`). A line that cannot be rewritten, or that still matches `/apikey/i` afterwards, becomes an empty line; a DASH manifest has its `apikey` parameters stripped (`stripDashApiKeys`) and is refused with 502 if it still names one. Range is never forwarded for `.m3u8` or `.mpd`: Stash honours it there, and a slice could start past `apikey=`. `isAllowedStreamPath` admits only Stash's stream files (`stream`, `stream.mp4`, `stream.webm`, `stream.mkv`, `stream.m3u8`, `stream.mpd`) and `stream.m3u8/<n>.ts`; `pickStreamQuery` forwards only `resolution` and `start`.
- `proxy.ts` serves previews, WebP sprites, images and clip previews. The scene, clip and image handlers find the entity by its route id (route id and `?instanceId=`, both required) and use that row's `stashInstanceId`. `proxyStashMedia` takes `?instanceId=` and accepts only the allowlist in `server/utils/stashMediaPath.ts`: Stash's media routes for the eight entity types by numeric id (`parseStashMediaPath`), with only the `t` (digits) and `default` (`true|false`) query keys rebuilt upstream. Sprite and VTT are id-keyed there; the hash-keyed paths Stash reports are refused. Stash image paths and marker streams are stored either absolute or relative, and the by-id handlers (`proxyClipPreview`, `proxyImage`) and the sync's preview probes (`processClipsBatch`, `reProbeUngeneratedClips`) rebase them onto the instance's address as it is now with `stashMediaUrl` (`utils/stashMediaPath.ts`: path and query kept, any `apikey` dropped and the instance's set, built with `URL`), so a changed Stash address takes effect at once and the key never goes to a stored host; a stored path holding `#` answers 404 (a probe skips it). Never concatenate `?apikey=` onto a stored path. All five handlers (`proxyScenePreview`, `proxySceneWebp`, `proxyStashMedia`, `proxyClipPreview`, `proxyImage`) forward the browser's `Range` and `If-Range` to Stash (`rangeHeaders`) and pass back `Accept-Ranges`, `Content-Range`, `ETag` and `Last-Modified` beside `Content-Type` and `Content-Length`, so a 206 reaches the browser whole; iOS Safari plays a `<video>` preview only from a server that answers ranges. A request without them sends none. Express hands a HEAD (the scene card's preview probe) to these GET handlers; it goes to Stash as HEAD (`upstreamMethod`), so no body is fetched and the slot is freed when the headers arrive. `proxy.ts` serves no manifests, so a range never slices past `apikey=`.
- Every media route requires `?instanceId=` (400 without, or for a malformed one); `getCredentials(instanceId)` serves only a named, enabled instance. The by-id routes read their row by (id, instance). `"default"` is an ordinary id (the owner's instance has it). A named instance that is not enabled (disabled or deleted) throws `UnknownInstanceError`, which both answer with 404. The by-id handlers pass the row's `stashInstanceId`.

## Authentication

- A Peek session is required on every `/api/proxy/*` route (`app.use("/api/proxy", authenticate)` in `server/initializers/api.ts`) and on the caption route.
- `authenticateStreamRequest` (`server/middleware/streamAuth.ts`) guards the stream routes: a request without `sig` needs the session; with `sig` it must be a link minted by `createExternalPlayerLink` (`utils/streamLink.ts`: HMAC over user, scene, instance, expiry and `passwordChangedAt`, keyed by HKDF from the JWT secret, 12-hour TTL), and signed links work on the direct stream (`proxy-stream/stream`) only. A password change or reset, or a JWT secret rotation, revokes every link; there is no per-link revocation.
- Every handler then runs `canUserLoadMedia` (`utils/mediaAccess.ts`), which checks each entity the path names with `canUserAccessEntity`, including scene plus clip for `scene_marker` media, and answers 404 when any fails. `proxyStashMedia` sets aside only the user's own `hidden` rows (`canUserSeeApartFromOwnHides`, mode `"apartFromOwnHides"`), so Hidden Items thumbnails load; a restriction, a cascade or a pending hold still refuses, and streams and captions check strictly. The by-id routes check access first (the check reads the row by id and instance), then read clip and image rows for their media paths; the scene routes read no row. Every refusal (missing, deleted, not visible, instance not enabled) answers the same `404 {error: "Not found"}`.
- Responses send `Cache-Control: private` (`utils/cacheControl.ts` keeps Stash's freshness and drops `public`), so a shared cache never serves one user's media to another.
- `paths.stream` and `paths.caption` on scenes are always null: the allowlist refuses both Stash routes and nothing reads them.

## Known and deliberate

- `streamProxy` swallows `AbortError` and `ERR_STREAM_PREMATURE_CLOSE`: seeking and navigating away produce them.
- `proxy.ts` sends at most 6 requests to Stash at once (the keep-alive agents' `maxSockets`) through `mediaProxyLimiter` (`utils/proxyLimiter.ts`). The rest wait by user: a free slot goes to the next user in turn (round robin), each user's own requests in the order they came, so one person's 250-card grid no longer queues ahead of everyone else. A user may have 300 waiting (one page's cards plus sprites at the 250 maximum) and 1,500 may wait in all; past either, or after 30 s waiting (under nginx's 60 s `proxy_read_timeout` on `/api/proxy/*`), `acquire` logs one warn with `activeCount`, `queuedCount` and the user's count and throws `ServiceUnavailableError` (503, `Retry-After: 1`), which `errorHandler` logs at warn, not error (a busy database's 503 stays an error). The sizes are reasoned, not measured: the warn shows the real numbers. A slot is freed (`Acquired.release`, idempotent) when the transfer's `stream.pipeline` finishes, when the client closes, on a request error and at the timeout. `tests/controllers/proxy.test.ts` fakes `http.get` and `stream.pipeline` (the fake completes at once); a fake that never calls back holds its slot, and the seventh request queues (its response needs `once` and `off`) until the 30 s limit refuses it. `proxy.http.test.ts` runs the real streams against a stand-in Stash; `proxyLimiter.test.ts` tests the queue alone.
- `proxyHttpRequest` streams with `stream.pipeline`, not `pipe`, which neither passes a source error on nor ends its destination. Once Stash's response has started, its status and Content-Length are promised, so a reset, a close or a stall (the timeout) mid-body destroys the response and the browser sees the request fail at once. The timeout is the upstream socket's idle timer, which also runs out while the browser holds the pipeline back (a paused preview, a background tab); it is armed again while `res.writableNeedDrain`, as in `pipeResponseToClient`, so only a silent Stash trips it. Before Stash answers, a failure answers 502 and the timeout 504; Stash's own 401/403/5xx are 502, 404 is 404, and 206/304/416 pass. A browser that leaves is logged at debug; Stash failing or going quiet at warn.
- `proxy.ts` drops a request whose client has gone (`res.destroyed`) before it joins the queue, and a waiting request whose browser leaves leaves the queue at once: each entry listens for its response's `close`, which removes it, clears its wait timer and resolves `acquire` with null (the listener goes when the entry leaves the queue, served, refused or timed out). A slot that comes just as the client leaves is freed instead of forwarded. A request waits on the session and access checks before the queue, and a grid of thumbnails is often abandoned mid-wait; forwarding it would fetch a response nobody reads and hold a slot meanwhile. Without the guard (and with `pipe`, which held such a slot until the upstream timeout) a full E2E run left the proxy starved for minutes.

## Downloads

- A playlist zip is read (`readDownloadableScenes`) when it is asked for (to size it) and again when it is built, for the download's `userId` (the requester, never the playlist owner), through `loadPlaylistItems` (`services/PlaylistQueryService.ts`) with that user's allowed instances, so its entries, M3U and NFOs hold only what they may see and the NFO's rating is theirs (`rating` from the scene builder; none writes none). Never read a scene, its relations or `rating100` with Prisma for a file a user receives.
- The scene and image file route (`getDownloadFile`) fetches through `fetchFromStash`: it forwards `Range` and `If-Range`, answers 206 and 416 as Stash does (with `Content-Range`, `Accept-Ranges`, `ETag`, `Last-Modified`), times out at 60 s before headers (504) and after 60 s without data, and cancels the body of a refused fetch (404 for Stash's 404 and 410, 502 for the rest). A zip row with no file is a 404; the zip itself gets Range from `res.sendFile`.
- A zip writes one entry at a time: the next scene is fetched only after the previous file is in the archive. archive and file stream share one `pipeline`, and any error aborts the job's fetch, the archive and the file, then marks the download FAILED with a fixed reason. A zip never emits an unhandled `error`: the process handler would exit the server. Each scene's fetch goes through `fetchFromStash` with the job's signal (60 s before headers); the byte counter fails the zip after 60 s without data (`ZIP_FAILED`) or past the size cap (`ZIP_TOO_LARGE`), and drives progress (bytes written of the planned sizes, up to 95).
- A scene the zip cannot fetch when it is built is left out and counted in `Download.skippedItems` (sent to the client): Stash answering 404 or 410 (its body is cancelled), or `getCredentials` throwing `UnknownInstanceError` (its instance disabled or deleted since the list was read). Anything else Stash answers, and any network error, fails the zip (`ZIP_FAILED`). The scene is fetched before its NFO is appended, so an NFO always has its video. A zip that leaves out every scene fails with `NOTHING_FETCHED` and leaves no file.
- Zips are built by `downloadJobQueue` (`services/DownloadJobQueue.ts`), one at a time (`ZIP_CONCURRENCY`), in the order asked for; start and retry only write the row and `enqueue`, never build in the request. A user has at most `MAX_ACTIVE_ZIPS_PER_USER` (3) PENDING or PROCESSING zips (429); a second start for a playlist whose zip is active returns that row; a retry sets FAILED to PENDING with one conditional `updateMany` (409 when it counts 0). The queue is memory only: the rows are the durable state.
- A build checks again when its turn comes, in order: the row exists (gone: nothing written), Can Download Playlists (`NO_PLAYLIST_PERMISSION`), playlist access (`PLAYLIST_NOT_FOUND`), a scene the user may see (`NOTHING_TO_DOWNLOAD`), `plannedZipBytes` within `maxPlaylistBytes()` (`ZIP_TOO_LARGE`), and, after `mkdir` of the user's folder (`statfs` throws ENOENT on a missing one), free space at least planned + 1 GiB (`NO_DISK_SPACE`). Progress, complete and fail writes are `updateMany` by id; a count of 0 means the row was deleted, and the build stops and removes its file. An abort with reason `"shutdown"` (`downloadJobQueue.stop()`, step 1 of the graceful shutdown) or `"cancelled"` removes the file and writes nothing.
- At startup, after `initializeCache()`, `recoverPendingDownloads()` sets every PLAYLIST row in PENDING or PROCESSING back to PENDING at 0 (one `dbWrite`), removes its partial file and enqueues it, oldest first. It skips ids the queue already holds: the server listens before the startup sync, so a zip can be asked for and started meanwhile. `resumeDownloadsAtStartup` (`initializers/downloads.ts`) runs it and then the sweep, each in its own try/catch: a failure is logged and startup goes on.
- File lifecycle: `deleteDownload` (controller) checks ownership with `getOwnedDownload`, then `downloadJobQueue.cancel(id)` (waits for the build to settle), then the service deletes the row and unlinks `filePath ?? zipPath(...)` of a PLAYLIST row (ENOENT ignored). `deleteUser` cancels the user's builds (`cancelUser`) after the delete unit and removes `userDownloadsDir(id)`; a failure there is logged, never the answer. `sweepOrphanedDownloadFiles` (`jobs/downloadCleanup.ts`, every hour after `cleanupExpiredDownloads` and once after `recoverPendingDownloads`) removes the `user-<n>` folder of a missing user and each `download-<n>.zip` that is neither `isActive` nor the `filePath` of a COMPLETED row; it ignores other names and never throws. Anything new that writes under the downloads folder must follow the `user-<id>/download-<id>.zip` shape or the sweep ignores it.
- Zip paths come from `utils/downloadPaths.ts` (`downloadsDir()`, `userDownloadsDir(userId)`, `zipPath(userId, downloadId)`, under `getConfigDir()`); the size cap and the queue's limits from `utils/downloadLimits.ts` (`MAX_PLAYLIST_DOWNLOAD_SIZE_MB`, an invalid value warns and uses 10240).
