# Stash sync

## Sync paths

- `fullSync`: every entity, then every post-sync step.
- `incrementalSync` and `smartIncrementalSync` (the startup path, from `SyncScheduler`): entities changed since the last sync, then the post-sync steps below.
- The daily full pass: `SyncScheduler`'s startup sync and each scheduled tick (`runScheduledSync`) call `fullSync()` instead when `fullPassDue` finds an enabled instance whose `StashInstance.lastFullPassAt` is older than `FULL_PASS_INTERVAL_MS` (24 h) or null; otherwise the tick runs `incrementalSync` and the startup `smartIncrementalSync`. A full-mode `syncInstance` that gets through its type loop adds its instance to `run.fullPasses`, and `runSync` writes `lastFullPassAt` for them after the post-sync steps (`recordFullPasses`). An abort, a restart or a failure before that records nothing, so the pass is still due; a type that failed does not hold it back (its `lastError` and watermark stay, and the incremental syncs keep trying it). Do not infer the pass from the types' `lastFullSyncActual`: a cut-off pass leaves recent times on its first types. `saveSyncState` still writes `lastFullSyncActual` for every "full" type whose pages all came back, an empty type included (the sync status's "last full sync"); its `lastFullSyncTimestamp` needs a `maxUpdatedAt`.
- All three take the lock and call `runSync(mode, instanceId?)`, which runs `syncInstance(instanceId, mode, run)` for the instance given or each enabled one, then `runPostSyncSteps(run.changes, { full })` once for the whole run. `syncInstance` syncs each type in `SYNC_ORDER` (`syncEntityType` picks full, incremental or skipped for the mode), then the cleanups, then (incremental paths) `refetchLinkedToDeleted` and `refetchGalleryMembers`.
- Every type goes through one page loop, `paginate(type, instanceId, { since, ids }, run)`, reading the type's spec in `ENTITY_SYNC`: `fetchPage` (its Stash query, 500 a page, narrowed by `since` or by ids; images by `image_ids`) and `processBatch` (its batch writer). A change to how a type is fetched or written goes in its spec, not in a loop of its own. The run's `SyncRunContext` carries the abort signal, checked between pages and passed to every request, and the run's `SyncChangeSet`. An empty id list fetches nothing: Stash reads it as no list.

## Change set

- `services/SyncChangeSet.ts`: each `processBatch` returns `BatchChanges` from `detectChanges` (what it wrote, what changed, the old and new far sides of changed entities, their studios, the performers/studios/groups whose tag set differs); `paginate` adds it to `run.changes`, and each cleanup adds its `deletedIds`. Past `SCOPE_LIMIT` (20,000) refs a type is "whole library" (`RefScope.whole`); `instances()` still names every instance with a change.
- Changed means new, `stashUpdatedAt` differs (clips: epoch ms), soft-deleted and back, or, for every type but images, a differing far-side set (and studio for scenes and galleries). An image's junction rows and studio are not compared: gallery inheritance writes into them.
- A batch reads its rows' stored state first, inside its transaction (`readStored`, one `json_each` statement; `CAST("stashUpdatedAt" AS TEXT)`, since sync stores Stash's text in a column declared DateTime and a raw read would parse it into a Date) and deletes junction rows with `DELETE ... RETURNING` (`deleteJunctionRows`), so the old far sides cost no extra read. A seed that wants to look "unchanged" must write `stashUpdatedAt` as text, as sync does; a Prisma `create` stores a number.
- A run that ends before its steps (abort, failure) leaves its change set in `carriedChanges`; the next run (a sync or `runCleanup`) takes it over.
- A refetch for a known link change passes `{ ...run, markChanged: true }` to `paginate`: every `processBatch` hands `run.markChanged` to `detectChanges`, which then counts each row changed with its old and new far sides and studios, whatever the diff finds (an image's links and a clip's primary tag are not diffed, and the rows come back with the same `updated_at`).

## Ordering

- Sync tags before anything that references them: junction rows such as `StudioTag` have foreign keys to `StashTag`, `foreign_keys` is ON, and `INSERT OR IGNORE` does not suppress foreign key errors. Every path, and its cleanups, goes in `SYNC_ORDER`: tags, studios, performers, groups, galleries, scenes, clips, images.
- A page can still reference what Peek has no row for: an entity created in Stash after its own type's pages ran, or of a type whose sync failed. Each spec's `references(items)` names what a page points at (junction far sides, a studio, a clip's scene and tags; only types before it in `SYNC_ORDER`), and `paginate` runs `ensureReferenced` before `processBatch`: one statement finds the missing ids (`missingReferences`, a `json_each` per type probing the primary key), and each type's missing ids are paged in by id (`paginate(type, instanceId, { ids }, run)`), their own references first, into the run's change set. All of it before the page's transaction opens. An id Stash no longer returns is not written, and the page's batch then fails on its foreign key and is retried by the next sync.
- One type's failure does not stop the others. `runEntityType` syncs a type (and, on the full path, cleans it up) and saves its `SyncState`: a Stash or database error becomes the type's `lastError` (through `describeStashError`), its timestamps stay, so the next sync retries it from its old "since", and the loop goes on. A cleanup that skips, refuses or fails adds its text after it (`recordEntityError` on the incremental paths); a smart sync that skips an unchanged type sets `lastError` to null. An abort is different: it throws `Error("Sync aborted")`, saves nothing, and ends the whole run, every instance (`getChangeCount` rethrows it too). The post-sync steps still run after a failed type: they are library-wide.
- The post-sync steps run once per run, after every instance (`runPostSyncSteps`). A full sync runs them all, whole library, in this order: scene tag inheritance, image gallery inheritance, entity image counts, user stats, tag scene counts, `recomputeAllUsers`. The incremental paths read the change set: gallery inheritance for the images written (even unchanged: their junction rows were rewritten) and the changed galleries' images (`galleryInheritanceScope`); then, when nothing changed, only the users with `pending` holds are recomputed, or nothing runs ("nothing changed, post-sync steps skipped"); otherwise scene tag inheritance for the scenes the changes reach (`sceneTagInheritanceScope`: the changed scenes, plus the scenes of every performer, studio and group whose tag set changed or that was soft-deleted, found through `ScenePerformer`, `StashScene.studioId` and `SceneGroup` with one `json_each` statement per source; the whole library when one of those kinds is past `SCOPE_LIMIT`), the image counts of the performers, studios and tags the changes reach (`imageCountScope`: changed images' and galleries' old and new far sides and studios, the links of galleries an image joined or left and of soft-deleted images and galleries, read by `countedThrough`, and every changed performer, studio and tag), user stats and tag counts, and `recomputeUsersForInstances(changes.instances())`. `runCleanup` (Apply deletions) runs the same steps for what it soft-deleted.
- First sync: each instance whose type loop ran to the end joins `run.synced`; one of them with `StashInstance.firstSyncedAt` NULL (new, or its URL changed) counts as a change, so even a run that found nothing recomputes its users, and `markFirstSynced` sets `firstSyncedAt` after the recompute unless a user whose scope covers it (`getUsersSelecting`) failed. Until then no user sees it (`getUserAllowedInstanceIds`, `EntityAccessService`). `runCleanup` marks nothing.

## Edits Stash makes without updated_at

- Stash's tag merge (`TagStore.Merge`) moves every link to the merged tag onto the kept one (scenes, images, galleries, performers, studios, groups, clip tags and a clip's primary tag) and deletes the merged tag; a performer merge does the same for scenes, images and galleries; deleting a studio clears it from its scenes, galleries and images. None of it moves the linking entities' `updated_at` (the kept tag or performer is updated, so its own row comes in).
- On the incremental paths and in `runCleanup`, after the cleanups, `refetchLinkedToDeleted` reads what live entities link to the rows they soft-deleted along `LINK_PATHS` (`linkedTo`: one statement per linked type, a `json_each` of the deleted ids driving each junction's reverse index or the `studioId`/`primaryTagId` index, then the linked row by primary key) and pages them in by id in `SYNC_ORDER`, marked changed. A failure joins that type's `lastError`; the linked rows keep their old links until a full sync. The full path skips it: every type after a cleaned-up one is fetched whole in the same run. A new path goes in `LINK_PATHS`.
- The consumers ignore soft-deleted far sides meanwhile: `SceneTagInheritanceService.processBatch` drops soft-deleted performers, studios, groups and tags (`softDeletedSources`, one statement per batch), `computeTagSceneCountsViaPerformers` joins a live `StashPerformer`, and gallery inheritance's inserts join a live `StashPerformer` or `StashTag`.
- Adding images to a gallery, removing them or editing its scenes from the gallery moves only the gallery's `updated_at`, and Peek writes `ImageGallery`/`SceneGallery` from the member's side. After `refetchLinkedToDeleted` (same places), `refetchGalleryMembers` pages in by id, marked changed, the scenes and images of every gallery in the run's `changed("gallery")` or `deleted("gallery")` on the instance: Peek's members (`linkedTo` along `GALLERY_MEMBER_PATHS`) and, for the changed ones, Stash's (`findSceneIDs`/`findImageIDs` with `galleries` INCLUDES, 500 galleries a request). A type fetched whole this run is skipped; past `SCOPE_LIMIT` galleries both types are fetched whole. An image's inherited values stay until it is written again, so this refetch is what makes a gallery's new studio, performers or tags reach its images. The replay evaluates that criterion (`applyCriteria` in `integration/stash-replay/library.ts`, images and scenes only).

## Timestamps

- Stash stores sub-second timestamps but returns whole seconds. `formatTimestampForStash` appends `.999`; without it, incremental sync fetches the entities from the last second again, forever.
- The "since" time is the newer of the last full and the last incremental sync (`getMostRecentSyncTime`).
- Every page asks for `sort: "updated_at", direction: ASC` (`pageFilter`), so an entity edited mid-sync moves to the end and is fetched again. The watermark (`newestUpdatedAt`) leaves out values more than `WATERMARK_MAX_SKEW_MS` (5 minutes) past the server's clock and `paginate` logs them once per type: a future-dated import would otherwise freeze incremental sync.
- Completeness: a type fetched whole (full sync, or never synced) collects the ids its pages returned (`seen`); after its cleanup, `fetchMissedIds` pages in by id the ones in the cleanup's `stashIds` that no page returned (an offset shift, or created mid-sync), into the change set. Not after a failed type or a cleanup without `stashIds`; a failure of it joins the type's `lastError`; the pages' watermark stays. The incremental paths do it in `cleanupEveryType` for their never-synced types (`seenIds` from `syncInstance`).
- `SyncState` is one row per instance and type (`stashInstanceId` NOT NULL). Every reader names its instances: `getSyncStatus` lists the configured instances (`GET /api/sync/status`, no address), and `isReady`, `getLastRefreshed` and the startup sync's full-or-smart choice read only the enabled instances' rows.

## Cleanup

`cleanupDeletedEntities` sets `deletedAt` on rows Stash no longer returns, for all eight types through one routine (`ENTITY_TABLES`, `CLEANUP_ID_FETCHERS`). A truncated id list from Stash would soft-delete the library, so it:

- skips when a page comes back empty before Stash's own count is reached (a partial list), and when Stash returns no ids while the cache has live rows;
- refuses, for every type, when more than `MAX_CLEANUP_DELETE_RATIO` (0.5) of the live rows would go and more than `CLEANUP_MIN_GUARDED_DELETES` (50), so a small library can still lose most of its rows;
- computes the delete set in one statement, `"id" NOT IN (SELECT value FROM json_each(?))` with Stash's whole list as one JSON parameter: no TEMP table (a TEMP table lives on one pooled connection, #526), no transaction, no bound-variable ceiling (Prisma's `notIn` binds one variable per id, and SQLite stops at 250,000). 178 ms for 260k image ids on the prod copy.

Keep all three when changing cleanup. `softDeleteMissing` writes 500 rows per `dbWrite` unit, binding `deletedAt` as epoch milliseconds, as Prisma stores a `DateTime`. The routine returns a `CleanupOutcome`: `deleted` and `deletedIds`, `stashIds` when it ran to the end, `skipped` for a guard's refusal, `error` for a failure. An abort rethrows. `skipped` is the text the type's `lastError` shows: `Cleanup skipped: ...` for a partial or empty list, `Cleanup refused: ...` with the counts for the ratio guard; a failure is stored as `Cleanup failed: ...`. Keep the prefixes: they are how a reader of `lastError` tells a refusal from a skip. A refusal's "Apply deletions" in the sync status posts `/api/sync/cleanup`, which calls `runCleanup(type, instanceId, { ignoreRatioGuard: true })`: it takes the lock as a sync (SyncBusyError, so 409, while a job runs), skips only the ratio guard, and writes the outcome to the type's `lastError`.

Merges (`MergeReconciliationService`): the scene branch soft-deletes first and then calls `reconcileDeletedScenes(instanceId, deleted)`, so scenes that leave Stash together are never each other's target. A scene merges only into the one live scene of its own instance sharing its phash; with several it waits in Merge Recovery. Each scene cleanup starts with `reconcileRecentDeletions`, the catch-up for scenes soft-deleted in the last 24 hours with activity and no `MergeRecord` as source.

## Deleting an instance

- Lock: the service runs one job at a time, `activeJob` (`"sync"` or `"instance-delete"`). `isSyncing()` is true while either holds it; `getSyncStatus().inProgress` only for a sync. `deleteInstance` throws `SyncBusyError` when the lock is held, and `deleteStashInstance` answers 409.
- Queue: a change already saved (an instance added, or its URL or key changed) calls `queueFullSync(id)`, which starts now or queues the sync for when the lock frees, and the response says `sync: "started" | "queued" | "none"`. `release()` starts one queued full sync, every instance first (it covers the ones queued singly); `abort()` drops the queue; `deleteInstance` drops its instance's entry. An explicit click answers 409 instead (`/api/sync/trigger`, `/api/stats/refresh-cache`).
- Background callers log an abort as "Sync aborted" at info through `logSyncFailure` (`utils/syncLog.ts`), and anything else at error level.
- Instance row first: one `dbWriteBatch` deletes the `StashInstance` row (`UserStashInstance` cascades), its `SyncState`, every user's own rows for it (history, the seven rating tables, image views, playlist entries, hides, entity downloads, merge records with it on either side) and the derived stats and rankings; rows with `instanceId = ''` stay. Then `stashInstanceManager.reload()`, and the request is answered.
- Cascade: the cached library goes afterwards, still under the lock. Junction rows go by their composite `ON DELETE CASCADE` keys; never delete a junction by a bare entity id, which removes the same id's rows on every instance.
- Chunked purge: `purgeInstanceCache` deletes 1,000 rows per `dbWrite` unit, `UserExcludedEntity` first (by id, since it has no `instanceId` index), then the eight entity tables, clips to tags, then `SyncState`. It checks the abort flag before every chunk and stops there.
- Startup sweep: `purgeUnknownInstanceCaches`, called by `initializeCache` before the scheduler starts, purges every instance id in the eight tables or `SyncState` without a `StashInstance` row, so a failed or aborted purge finishes at the next start. It does nothing when no instance exists.

## Stash requests

- Every `StashClient` request fails after `STASH_REQUEST_TIMEOUT_MS` (120 s) with `StashRequestTimeoutError`. While a job holds the lock, `getStashClient` returns `client.withSignal(abortController.signal)`, so `abort()` ends a request in flight with `Error("Sync aborted")`. A test's stub client used under the lock needs `withSignal` (returning the stub).
- Report a Stash failure through `describeStashError`: a graphql-request `ClientError`'s own message embeds the query and its variables. It gives the operation, each GraphQL message with its `path` (the field that broke) and the HTTP status.

## Raw SQL

Every `processBatch` writes its page in one transaction (`writeBatch`, a `dbWriteTransaction` labelled `sync.<plural>`), one statement after another on `tx`: the stored-state read, the junction deletes `RETURNING`, the entity upsert, the junction inserts, then, with the diff (`detect`) in hand, the holds (`holdForRecompute` on `tx`, for the users `usersToHold` read before the transaction; see `exclusions.md`, "Holds during sync"). `writeBatch` returns the batch's `BatchChanges`. A failure rolls the page back whole, holds included, the type records `lastError` and keeps its watermark. Everything is built before the transaction opens; no Stash request (a page's missing references, the clip preview probe) and no `dbWrite` runs inside it. A scene batch holds the lock about 0.1 s on a 200k-scene library, an image batch under 0.08 s.

Junction inserts are bound: `insertJunctionRows` passes the rows as one JSON parameter (`[nearId, farId]`, SceneGroup adds `sceneIndex`), so a statement does not grow with the page. The entity upserts still build their VALUES with `escapeSql()` and string interpolation: keep the escaping when touching them, and use `?` parameters in new code.

The performer, studio and tag upserts leave `imageCount` out of their `ON CONFLICT` lists: the stored count includes gallery inheritance, and the scoped rebuild only recounts what changed, so an update that wrote Stash's direct count would stay wrong.

A scoped post-sync statement binds its refs as one JSON parameter of `[id, instanceId]` pairs (`pairsJson`) and drives from it with `json_each(?) j CROSS JOIN <table> ON ... = json_extract(j.value, '$[0]')`, or filters an UPDATE with a single-column `rowid IN (...)` of that; a row-value `(id, stashInstanceId) IN (...)` scans. A correlated count must correlate inside each arm of its UNION: a count over a UNION of every pair, filtered afterwards, recomputes the UNION per counted row.

## Tests

- `server/tests/services/StashSyncService.paginate.test.ts` pins the page loop (stubbed specs) and each spec's request variables (a stubbed client). Integration tests write rows through a spec's `processBatch` (`ENTITY_SYNC.scene.processBatch(rows, instanceId, run)`) instead of a whole sync, or run the page loop (`stashSyncService["paginate"](type, instanceId, {}, run)`) with a stub client when a test needs `ensureReferenced`.
- `server/integration/helpers/statementRecorder.ts` records the statements a batch sends, on the main client and inside its transactions, with the most in flight at once (`vi.spyOn` cannot wrap Prisma's client). `StashSyncService.junctions` and `.clips` use it to pin one transaction per page, statements one at a time.
- `server/tests/services/StashSyncService.cleanup.test.ts` mocks Prisma with `tests/helpers/prismaMock.ts`, routes `$queryRawUnsafe` by statement shape and spies on `dbWrite`.
- Real-SQLite coverage is in `server/integration/services/StashSyncService.cleanup.integration.test.ts`, every type: it seeds rows under two made-up instances with the same ids, which real sync never touches, and spies on `stashInstanceManager.get` to page what Stash returns.
