# Client

## Data

- List pages fetch through the TanStack Query hooks in `src/api/hooks/`, keyed by `src/api/queryKeys.ts`. The key factory has an instanceId slot, but the list pages pass none, so every list key is `[entity, undefined, "list", params]`.
- The five entity detail pages (performer, studio, tag, collection, gallery) read their entity through `useEntityDetail` (`api/hooks/useEntityDetail.ts`) and render in `components/detail/` (`EntityDetailPage`, `EntityDetailLayout` and its parts); no page calls `libraryApi` for its entity, and the by-id lookup is `findEntityById` (typed per page, used only by that hook). The Scene page stays out of the layout; `ScenePlayerContext` loads its scene.
- Every rating and favorite write goes through `useUpdateRating` and `useUpdateFavorite` (cards, the player, the lightbox and the detail pages), never `libraryApi.updateRating`/`updateFavorite` directly in new code. They patch every cached row and detail entry of the entity (`patchEntityInCache`, `api/entityCache.ts`) before the server answers, put it back on failure, write the server's value on success, and mark the library stale without refetching (`markLibraryStale`). Overlapping writes of one field share a slot (`api/userDataWrite.ts`): only the last to settle writes the cache, and requests in flight for the entity's lists are cancelled around each write. A host's `onRatingChange`/`onFavoriteChange` is for local state only; the lightbox never writes the cached page itself.
- A scene's clips are `useSceneClips` (`api/hooks/useSceneClips.ts`, keyed `queryKeys.clips.forScene(sceneId, instanceId)`): the player's timeline and the details panel share it, and neither fetches clips itself. A keyed query that keeps its previous answer on screen (`placeholderData`) keeps it only for the same entity, as `useSimilarScenes` does for the next page of one scene, never across scenes.
- A detail tab passes its lock as `lockedFilters: { <entity>_filter: {...} }`, and `SearchableGrid` merges it into the panel's filter, the lock winning on a clash. An Images tab is `DetailImagesTab` (`components/detail/`): the Images list itself, locked to the page's entity, with its own `image_<type>` presets; there is no separate image grid or paging hook for a detail page. The Include sub-studios/sub-tags toggle shows only on tabs whose field takes a depth in the contract, and sends `depth: -1` there.
- `useEntityDetail(type, id, urlInstance)` returns one state: `loading` (also for a new id, never the previous entity, and while the library initializes), `notFound` (missing, hidden or restricted alike), `ambiguous` (an id on several servers: the server's 400 with `matches`, a link per server) and `error` with `retry`. A found entity carries its own `instanceId` and `ref`, which every read, filter and write uses, and the viewer's cached `rating` and `favorite` with `setRating`, `setFavorite`, `toggleFavorite` (the rating hotkeys are inside). Pages show `EntityNotFound` for the first three and an error with Retry; the Scene page maps `sceneError` through `describeLookupFailure` (`api/lookupFailure.ts`).
- The library-initializing state is one query, `queryKeys.library.ready`, in `api/hooks/useLibraryReady.ts`. A query answered 503 `ready: false` is not retried: the query cache's `onError` marks the library not ready, and `useLibraryReady` then asks `GET /api/library/ready` every 5 s and, once it says ready, invalidates the library's lists, details, clips and carousels. Pages render `LibraryInitializingBanner` and treat `isLibraryInitializing(error)` as loading, never as the error page; a query that should wait takes `enabled: ready` from `useLibraryReady()`. No component retries on its own. A busy 503 (Retry-After up to 10 s) is retried once after that wait; mutations never retry.
- `src/api/client.ts` holds `apiFetch`. Only a 401 (a lost session) redirects to login, and never from `AUTH_SILENT_ENDPOINTS` (background pings, which throw so they can't interrupt playback; add new fire-and-forget endpoints there), `/auth/*` endpoints or a page in `PUBLIC_ROUTES` (`constants/navigation.ts`, which `App.tsx` declares its public routes from). A 403 or any other failure throws `ApiError`; show it with `getErrorMessage(err, fallback)`, which adds the wait to a 423 or 429. The server answers 401 only for a lost session.
- TanStack Query handles cancellation of its own queries. Code that aborts a fetch itself must swallow the `AbortError`; the image proxy's callers do it with `.catch(() => {})`.
- The hooks don't wait for auth themselves; `ProtectedRoute` holds back rendering until auth resolves. A component outside it gates its own queries.
- Entity references in URLs and filter values are `"id:instanceId"`, built by `src/utils/compositeKey.ts`; a bare id means no instance was known.
- A card's count opens a list through `getFilteredListPath` (`utils/entityLinks.ts`), built from that page's filter options: the singular param of the page's option for the entity type (`/scenes?tagId=5`) plus `instance`, which `urlParamsToFilters` joins into `id:instance`. A page with no such option gets no link.
- After a Stash instance is added, edited, enabled, disabled or deleted, or a user's Content Sources change, call `invalidateInstanceQueries(queryClient)` (`api/hooks/useLibraryReady.ts`): the setup status and the library queries (`invalidateLibraryQueries`).
- A card's `onHideSuccess(entityId, entityType, instanceId?)` carries the entity's instance, and list handlers remove the hidden item by `makeCompositeKey(id, instanceId)`, never by bare id. `useHideBulkAction` never sends a selection entry without an instance; it counts that entry as failed.
- After a hide, bulk hide, restore or Restore All, `useHiddenEntities` calls `invalidateExclusionDependents` (library queries, Recommended, stats; Hidden Items marked stale, not refetched). `invalidateInstanceQueries` calls it too. A new query that shows the user's visible set belongs under a root the library predicate matches, or in that helper.
- User settings come from `useUserSettings()` (`api/hooks/useUserSettings.ts`); saves go through `useUpdateUserSettings()`, which updates the cache before the server answers (a refused save refetches, so every reader shows the server's value again). Every reader of a stored preference, the providers included, reads `useUserSettings`; nothing else GETs or PUTs `/user/settings`. `useAuth().user` holds identity and permissions, not preferences. Filter presets come from `useFilterPresets()`/`useDefaultPresets()` (`api/hooks/usePresets.ts`); after a save, delete or default change call `invalidatePresets`.
- Every authenticated answer carries the library stamp in `X-Peek-Library` (`server/services/LibraryStamp.ts`); the server moves it after a sync, a Stash server change, and an admin's change to the user's restrictions or role. The stamp is `<boot>.<library>.<user>`. `apiFetch` records the first stamp it sees and acts only on a newer one (any answer, errors included): another boot, or on the same boot a higher library or user counter (it keeps the highest of each, so a late answer carrying an older stamp does nothing). It then calls the listener `createQueryClient` registers: `invalidateExclusionDependents` (what is on screen refetches, the rest goes stale). The user's own hides and Content Sources changes do not move it (the client already invalidates). `resetLibraryStamp()` runs on logout and in tests' `afterEach`. A test that mocks `api/client` and loads `api/queryClient` provides `setLibraryStampListener`.
- `logout` removes the post-login redirect, clears the query cache and does a full load of /login.
- Detail pages take their tab counts from `useRelationCounts` (the tabs show `TAB_COUNT_LOADING` and none opens until it answers) and filter, read and count on the loaded entity's `instanceId`, never the URL's `instance` param (a bare-id link has none).
- Every write component and API call takes the entity's `instanceId` as a required string (`hideEntity`, `EntityMenu`, `libraryApi.updateRating`/`updateFavorite`, `useHideBulkAction`). A cache update for a list row matches by `makeCompositeKey(id, instanceId)`, never the bare id.

## List state

List state lives in the URL: `useListUrlState` (`hooks/useListUrlState.ts`) derives it on every render from `useSearchParams` and the cached presets, per field: the URL, else the default preset, else the entity default. "The URL has filters" is decided by the entity's `UI_KEYS`, `q` and `filters=none` only (`instance`, `tab` and presentation keys never disable the preset). Clearing the filters (Clear All, the last chip, a preset without filters) writes `filters=none`, which is list-owned and never sent. Setters rewrite only the list's own keys (`listOwnedKeys`) and keep the page's (`tab`, `instance`, `includeSub*`, `image`). Push for filters, sort, page, folder and presets; replace for search text, per page, view, zoom, density, timeline period and lightbox paging. A random sort keeps its seed in the URL. The request is `buildListQuery(entity, state, permanentFilters)`, permanent filters last. Never copy list state into `useState`.

## Structure

- Provider order in `App.tsx`: Auth, QueryClient, Theme, Config, UnitPreference, TVMode, ShortcutScope, CardDisplaySettings. The theme follows the account: `ThemeProvider` applies `settings.theme` from `useUserSettings`, else the browser's last key (`themes/themeCache.ts`, localStorage `app-theme`), else peek; a key that names no theme paints peek, except a custom key while the custom themes load, which keeps what is painted. `main.tsx` applies the cached variables (`app-theme-vars`, built-in themes only, peek's for a custom one) before rendering, and `base.css` declares peek's on `:root` (`tests/themes/baseCssDefaults.test.ts` keeps them equal to `themes.ts`), so no page paints unstyled. `changeTheme` saves through `useUpdateUserSettings`. Custom theme keys go through `customThemeKey`/`parseCustomThemeKey` (`shared/types/themes.ts`). The root providers load user data only while `isAuthenticated`; `ConfigProvider` and the route gate (`SetupStatusGate`) read the one setup-status query, `useSetupStatus` (`queryKeys.setup.status()`), which retries every failure with back-off and never turns one into "setup not complete"; the app's routes render only from a loaded status.
- Keys go through `useShortcutScope` (`hooks/useShortcutScope.ts`; the dispatcher is `contexts/shortcutDispatcher.ts`): layers global < tv < page < player < overlay, and an overlay is modal (the lightbox, `useFocusTrap` dialogs, the help dialog). No component adds a `document` or `window` keydown listener for shortcuts; element `onKeyDown` handlers run first, and a handled key calls `preventDefault`. Video keys act only while focus is in the player or on nothing. video.js stops keys on its own controls, so the player hands them over through `userActions.hotkeys` (`usePlayerHotkeys`, which calls `dispatcher.dispatch`); a control's own keys (Space on a button, slider arrows) never reach it.
- TV mode moves DOM focus by position: `TVNavigator` (a `tv` scope `GlobalLayout` mounts while `isTVMode`) calls `moveFocus` (`utils/spatialFocus.ts`) inside `topModalRoot() ?? document.body`, searching the focused item's group, then its cell grid (a `[data-tv-cells]` container, such as the filter panel's grid: same cell first, then the nearest cell that way), then its region (`main`, `aside`). Across a move, the narrower box's overhang decides, so a full-width bar's Down lands on the row's first item. Cards are TV items through `CardContainer` (`data-tv-item`); other candidates are naturally focusable elements. In TV mode a closed select hands its arrows to the navigator (Enter or Space opens it) and a slider keeps only Left and Right (`targetOwnsKey`, `isTVModeOn`). No page wires TV navigation: no column tables, item refs, zone props or `useInitialFocus`. A grid that needs its column count measures it with `useRenderedColumns`. PageUp/PageDown belong to `SearchControls`' page scope, enabled only in TV mode.
- A dialog is `Modal` (`components/ui/Modal.tsx`): portalled to `document.body`, `role="dialog"` labelled by its title, focus trapped and returned to the opener, a modal overlay scope (no page or global key runs), and Escape, a backdrop click (one that started on the backdrop) or the close button call `onClose` unless `dismissible={false}`. `ConfirmDialog` is built on it. The backdrop stops click and mousedown, native ones included, so an outside-press listener (a dropdown or popover that can sit in a dialog) goes on `document` in the capture phase. Don't hand-roll an overlay.
- Questions to the user go through `useConfirmDialog` (`hooks/useConfirmDialog.tsx`, which renders `ConfirmDialog` on `Modal` and answers no on Cancel, Escape, the backdrop or unmount), never native `confirm()`, `alert()` or `prompt()`; lint rejects them.
- A banner or inline status is `StatusMessage` (`components/ui/StatusMessage.tsx`: error, warning, info or success; error is `role="alert"`). Don't hand-roll status colours; use the `--status-*` theme variables (a test rejects hard-coded ones).
- New code uses theme CSS variables (`var(--bg-card)`, `var(--accent-primary)`). About 50 Tailwind palette classes remain, mostly spinners, grays and status colors; don't copy them. The `visual-style` skill has the full system.
- A list's filter panel is its rows in the shared panel table (`shared/types/filters/panel/`, one file per list, `PANEL_FIELDS`), each on a field of the list's contract table (`shared/types/filters/fields.ts`): a new filter starts with a row there, and nothing in the client names the field. `src/utils/filterFields/` reads the rows: `filterOptionsOf(kind, unitPreference)` (`options.ts`) draws the panel's options, and each editor kind's codec (`codecs.ts`, `CODECS`: ref, number, date, text, enum, choice, toggle) holds its keys and builds its criterion (`toCriterion`); `buildPanelFilter(kind, state)` (`build.ts`; the state is metric, nothing converts: an imperial viewer's editors convert on screen) walks the rows, then applies a page's permanent criteria (a ref merges with the panel's picks, the panel's modifier when its picker offers it; a `{ start, end }` date goes through the date codec; `undefined` sends nothing; anything else wins) and nests a field with a `path` (`scenes_filter.groups`); clips build a `clip_filter` like every list, which `POST /api/library/clips` takes (`GET /api/clips` keeps reading the old parameters for old callers). The modules import only relative paths and `@peek/shared-types` (the server's integration walk loads them). `src/utils/filterConfig.ts` keeps the per-list names (`SCENE_FILTER_OPTIONS`, `buildSceneFilter`, ... as typed wrappers returning the shared wire types), the sort options and the carousel definitions. `tests/utils/filterContract.test.ts` fails when the options drift from `UI_KEYS` and `SORTS`, and `tests/utils/filterGolden.test.ts` pins each list's options, requests and URLs in `tests/utils/__golden__/`.
